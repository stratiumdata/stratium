# Phase 14 — The admin plane (`stratium-pap`)

Implements spec §3.2 **A3**/**A5**, §6.4, §4.10 **N1**–**N14**, and §4.4.3
**T4**–**T6**. Closes conformance property **C5**. Eight tasks.

**What this makes true.** Four rulings currently defer writes to "the control
plane" and point at nothing: **E7** (approvals), **T1** (tool catalog), **V1**
(epoch bumps), **V4** (delegation revocation). Every one is exercised today only
by integration tests writing directly to the database. This phase is the
component they have all been deferring to.

**Ordering is the risk control.** §6.4's three items — CRUD, authoring, UI — are
built in that order, each proven before the next depends on it. A UI over an
unproven write path would make a defect in the write path look like a UI bug,
which is the most expensive place for one to hide.

**The PAP is the most privileged component in the system, and the only
internet-facing one.** It holds exactly the write credentials the PDP is
deliberately denied. Nothing in this phase may weaken that asymmetry: the PDP
keeps `SELECT` only on `approvals` and `tool_catalog`, because those absent
grants *are* E7's and T1's enforcement.

## Global constraints

- Go 1.25, module path `stratium`, module root `services/`.
- **Single-tenant per process** (**N1**). The tenant is fixed at startup from
  configuration, exactly as every PDP is. **No request may carry a tenant**, and
  no code path may resolve one. A cross-tenant write must be structurally
  impossible, not prevented by a check.
- **No `WHERE tenant_id` in any Go query.** RLS remains the only tenant
  boundary.
- **No authentication fallback of any kind** (**N2**, §8). OIDC against the
  customer's IdP or nothing. The deleted `MockValidateToken` / `ParseUnverified`
  path is not to reappear in any form, including "for local development".
- **Every write is audited** (**N4**) into the same hash chain, in the same
  transaction as the write it records. An unaudited write is a change nobody can
  attribute.
- **The PDP's grants do not change** (**N3**).
- **Fail closed.** An unverifiable token, an absent role claim, an unreadable
  config value — each refuses the request. On an admin plane a fail-open is
  total.
- **Never log a bearer token, an operator's claims, or policy text.**
- `internal/authz` stays pure and is not touched.
- Strict root `.golangci.yml`. Clean before each commit, from `services/`:
  `go build ./...`, `go vet ./...`, `go vet -tags integration ./...`,
  `go test -race ./...`, `golangci-lint run ./...`. Plus `make conformance` and
  `make integration` from the repo root.
- Conventional commits, no attribution trailers — check each message.
- Scratch work goes in the session scratchpad, never the repository.

## Task 1 — Identity, roles, and the tenant boundary

**Files:** `services/cmd/stratium-pap/` (new), and tests. **No writes yet.**

An HTTP server that verifies an OIDC bearer token against the customer's IdP and
resolves a role, and nothing else. Every route returns "not implemented" until
Task 3 — but returns it *only* to a verified operator with a sufficient role, so
the security foundation is proven before anything can use it.

**Verification is real.** Discover the IdP's JWKS from its issuer, verify the
signature, check `iss`, `aud`, and expiry. **No fallback, no dev mode, no
"skip verification if unset"** — spec §8 deleted that path rather than gating it,
and a gate is how it comes back.

**Roles come from a configured claim** (**N2**): `viewer`, `editor`, `admin`. An
absent or unrecognised claim value is **not** a default role — it is a refusal.
Map claim values to roles in configuration so a customer's existing group names
work without a table.

**The tenant is startup configuration and appears in no request** (**N1**).
Assert that structurally: no handler signature, no route, and no request body may
carry one. This is the property that makes a cross-tenant write impossible
rather than merely checked.

**Required config has no defaults**, and a missing value fails at startup naming
every missing key at once.

**Tests:** a valid token with a sufficient role reaches the handler; an expired,
wrongly-signed, wrong-audience, wrong-issuer, or malformed token is refused; an
absent role claim is refused; an insufficient role is refused; **no route accepts
a tenant in any form**; a missing config value fails startup naming all.

**Mutation-test and report survivors:** accept an unverified token; treat an
absent role claim as `viewer`; allow a tenant to be supplied per request; skip
the audience check.

## Task 2 — The database role

**Files:** a migration, and integration tests.

A `stratium_pap` role with `INSERT`/`UPDATE` on `policies`, `agents`,
`tier_overrides`, `tool_catalog`, `approvals`, and `delegations`, plus
`INSERT`/`SELECT` on `audit_chain` — the same treatment `stratium_app` has, so
the append-only rules protect a second writer identically.

**The PDP's grants do not change** (**N3**). Prove it: an integration test
asserting `stratium_app` still cannot `UPDATE` `approvals` or `tool_catalog`
after this migration. Those absent grants are E7's and T1's enforcement, and a
migration that widened them by accident would silently undo two rulings.

**Phase 12's epoch trigger fires on these writes** — that is the point, and it
already works for any role. Test that a write as `stratium_pap` bumps the epoch,
since every prior test bumped as the owner or the serving role.

**Tests:** each table is writable by `stratium_pap` and the write bumps the
epoch; `stratium_app` still cannot write `approvals` or `tool_catalog`;
`audit_chain` remains append-only for `stratium_pap` — `UPDATE` and `DELETE` do
nothing, as the rules require.

## Task 3 — CRUD: policies, agents, tier overrides

**Files:** `services/cmd/stratium-pap/`, and tests. **Closes C5.**

Create, read, update, delete for the three tables A5 names first. **Every write
is audited in the same transaction** (**N4**), as a new `EventType` recording
who did what.

**Validate before persisting.** A policy is checked with its engine's own
`Validate` — all four engines already implement it, and Phase 4a made those
checks strict enough to reject a policy that would be semantically dead. Storing
a policy that can never fire is the failure the PAP exists to prevent.

**Tier overrides are raise-only** (§4.4). `ValidateOverride` already enforces
this and has had no production caller since it was written — this is it. An
override that lowers a built-in tier is refused.

**Role gating:** `viewer` reads, `editor` writes, `admin` writes and deletes.
State the mapping and test each boundary.

**Mutation-test and report survivors:** persist without auditing; skip
`Validate`; accept a lowering override; let `viewer` write.

## Task 4 — CRUD: tool catalog, approvals, delegation revocation

**Files:** `services/cmd/stratium-pap/`, and tests. **Makes T1, E7, and V4
real.**

The three writes later phases deferred here:

- **Tool catalog** (**T1**) — rows naming a tool's tier, verb, and which
  `raw_input` fields carry its resource identity and command. Remember a NULL
  tier with a `command_field` means "extract and classify", which is `Bash`.
- **Approvals** (**E7**) — the approve action itself. The PDP cannot do this and
  must not gain the grant. **Enforce that the approver is the chain's root
  principal**; the PDP checks this at consumption time, and checking it at
  approval time too means a bad approval is never written rather than written and
  later refused.
- **Delegation revocation** (**V4**) — setting `revoked` and `revoked_at`.
  Enforcement already exists at every hop of `DelegationLeg`, so this only
  supplies the write. Confirm cascade holds: revoking a root denies every
  descendant on the next action.

**Every write audited, in the same transaction** (**N4**).

**Mutation-test and report survivors:** approve as someone other than the root
principal; revoke without auditing; write a catalog row with neither a tier nor
a `command_field` (the database `CHECK` should already refuse it — confirm the
API surfaces that rather than crashing).

## Task 5 — Authoring: validate and test-against-sample-input

**Files:** `services/cmd/stratium-pap/`, and tests.

Two endpoints an operator can use before committing a change:

- **Validate** — run a policy's text through its engine's `Validate` without
  persisting. All four engines implement it.
- **Test against sample input** — evaluate a candidate policy against an
  operator-supplied `EvaluationInput` and return the verdicts, without
  persisting anything.

**Neither may write.** A dry-run that mutates is not a dry-run; assert no
database write occurs on either path.

**Dry-run replay against recorded decisions is deferred** (**N6**). §4.9 stores
only `InputDigest`, never raw input, so a replay can reuse a recorded derived
tier but cannot re-derive one. **Document the gap and what would unblock it
(C17)** rather than shipping a replay that silently answers a narrower question
than an operator would assume.

## Task 6 — The admin UI

**Files:** `ui/` (new), served by the PAP.

React/Vite/shadcn, per §6.4 item 16, re-scoped to agent authorization: policies,
agents, tier overrides, the tool catalog, pending approvals, and delegations
with a revoke action.

**It is a client of the API Tasks 3–5 proved, and adds no authorization of its
own.** Hiding a button is not enforcement; every action must already be refused
server-side for an operator lacking the role, and the UI merely reflects that.
Test that a `viewer`'s session cannot perform a write even with the client
bypassed.

**The token is the operator's OIDC token**, obtained by standard browser flow
against the customer's IdP. The UI stores no credential of its own and the PAP
issues none.

## Task 7 — Make tier overrides reach a decision

**Files:** a migration, `services/internal/store/`,
`services/internal/pdpgrpc/server.go`, `services/cmd/stratium-pap/`, and tests.
Implements §4.4.3 **T4**–**T6**.

**The override step of §4.4's resolution order has never run in production.**
`TierTable.Overrides` is read at one place — the first loop of
`deriveTierByName` — and assigned nowhere outside `tier_test.go` and
`catalog_test.go`. The PDP builds its table with `Catalog` alone. `stratium_app`
holds no grant on `tier_overrides`, not even `SELECT`.

Task 3 shipped full CRUD over that table and gave `ValidateOverride` its first
production caller. An operator can create an override, be correctly refused a
lowering one, and have the result reach nothing. **This task is why Task 8's
proof 6 and the C5 assessment can mean anything at all** — until overrides are
live, "an override from an agent-writable source is never honored" is true only
because no override is honored.

**T4 — load them.** `GRANT SELECT` (and nothing else — **T6**) on
`tier_overrides` to `stratium_app`. Read them tenant-scoped on the decision
path, exactly as policies and catalog entries already are, and key the map with
the same `lookupKeys` the catalog uses. **Preserve V3's ordering**: the epoch is
read first, before any other read in `Decide`, and this new read must not
displace it. Phase 12's trigger already fires on `tier_overrides` writes, so
invalidation needs nothing new — confirm that rather than adding to it.

**T5 — raise-only compares against the resolution beneath the override**: the
catalog entry where one exists, the built-in otherwise. Today
`ValidateOverride` compares against built-in alone, so built-in `READ` + catalog
`DESTRUCTIVE` + override `WRITE` passes validation and then lowers the effective
tier. Enforce the corrected baseline **at both ends** — at write time in the
PAP, so an operator gets an error instead of an inert row, and again when the
PDP builds the table, because a direct `INSERT` as a superuser never touches the
PAP. **A row failing the read-time check is dropped and surfaced, never silently
honored.** Dropping falls back to the higher tier beneath it; failing the whole
decision would let one bad row deny an entire tenant.

**C4 asserts the old contract.** `TestC4_TierOverrideRaiseOnly` pins raise-only
as it stands. Update it to the corrected baseline, and say in the report what it
asserted before and after — a conformance property changing meaning is exactly
the thing that must not happen quietly.

**Tests:** an override raises a tool's tier and the change reaches a real
`Decide`; an override at or above its baseline is honored; one below it is
refused at write time; one written directly to the database below its baseline
is dropped at read time and surfaced; the catalog case and the built-in case are
both covered, since they are different baselines; `stratium_app` still cannot
write `tier_overrides`; the epoch bumps on an override write.

**Mutation-test and report survivors:** keep comparing to built-in only; honor a
dropped row instead of dropping it; grant `stratium_app` `INSERT` and confirm a
test notices; read overrides before the epoch and confirm V3's ordering test
catches it.

## Task 8 — Prove it, and the conformance sweep

**Files:** `deploy/docker/`, the integration suite,
`services/internal/authz/conformance_test.go`.

**The PAP has no compose service, and there is no auth fallback (N2).** Both
have to be solved before any proof can run. Add a **real IdP** — Dex — and a
`stratium-pap` service, and obtain genuine tokens per role. Every surface in
this project was proven against the real thing it was built for, and each such
run found something no constructed test had; Task 6's own fix round was a real
IdP's token endpoint sitting on a different origin than its issuer, which broke
the CSP and which no hand-built fixture had suggested. **Do not substitute a
hand-rolled token issuer** — inventing the claim shapes defeats the point.

Follow the established isolation pattern: a dedicated PDP service and its own
`STRATIUM_TENANT_ID`, as `pdp-epoch` and `pdp-cache` already do. These proofs
mutate control-plane state and bump the tenant epoch, which would disturb any
test sharing a tenant.

**The IdP must emit an array-valued groups claim.** `resolveRole` handles both a
string claim and an array, and the array branch carries logic the string branch
does not: when an operator matches several groups it takes the **highest** role.
That is the branch every real deployment uses and the one where a wrong answer
silently over-privileges someone, and it is only unit-tested today. Dex's static
passwords may not carry per-user groups; if they cannot, use a connector that
does, or a heavier IdP such as Keycloak. **Do not settle for mapping `email`** —
that exercises the string branch and leaves production's shape unproven. If this
turns out to need disproportionate setup, say so and stop rather than quietly
downgrading the claim.

**Fix the `audit_chain` landmine first, before adding any test.**
`store_integration_test.go`'s `proof6` revokes `INSERT ON audit_chain` from
`stratium_app` and `stratium_audit_owner` and never restores it, under a comment
claiming "which is why it runs last" — **it is not last**;
`tenant_epoch_integration_test.go` sorts after it. Any integration file that
sorts after `store_` and calls `Decide` fails with "permission denied for table
audit_chain" in the full suite while passing in isolation. Task 7 routed around
it by naming its file `decide_tier_override_integration_test.go`, so that
**filename is now load-bearing**.

Restore both grants in a `t.Cleanup`. "Deliberately irreversible" is a statement
of consequence, not of impossibility. **Verify the restore actually works rather
than assuming it** — a half-working restore turns a loud failure into a flaky
one, which is worse than the trap it replaces. Then confirm the constraint is
gone by renaming Task 7's file to something sorting *after* `store_` and
watching the suite still pass; restore the name afterward either way.

**Proof 4 extends the existing `extauthz` escalation proof rather than building
a new one.** Phase 10 already proves deny → approve out of band → retry
succeeds; the only change is that the approval now goes through the PAP's API
instead of a direct database write. That is the smallest change that proves
**E7**, and it keeps the claim sharp: the PAP holds the `UPDATE` grant and the
PDP still does not.

**Proof 6 must exercise both raise-only baselines.** §4.4.3 **T5** made the
baseline the resolution *beneath* the override — the catalog entry where one
exists, the built-in otherwise. Those are different code paths, so a proof
covering only one covers half the rule.

**Against a live stack:**

1. An `admin` creates a policy; the epoch bumps; the next PDP `Decide` reflects
   it. The full loop: admin plane writes, trigger fires, decision plane observes.
2. A `viewer` is refused every write.
3. An unverified token is refused everywhere.
4. Approving an escalation through the PAP lets the agent's retry succeed —
   **E7** end to end, with the PDP still holding no `UPDATE` grant.
5. Revoking a root delegation through the PAP denies every descendant on the
   next action — **V4** and cascade.
6. A tier override created through the PAP raises a tool's tier and is refused
   when it would lower one — **C5**.

**Then assess C5 — and note that this plan previously described it wrongly.**
It was summarized here as "the PAP override write path exists." The spec says
something materially different: **"A tier override from an agent-writable source
is never honored"**, and the test is named
`TestC5_AgentWritableOverrideNotHonored`. That is a **D1** property about the
policed component not declaring its own authority — the write path is only one
of its supports. Its skip reason cites the missing write path, which is what
caused the confusion.

Read the property, not the summary. Once Task 7 makes overrides live, C5 rests
on four mechanisms that must be pointed at **together**: no PEP sends
`declared_tier` (asserted on all four surfaces); `CheckDeclaredTier` cross-checks
rather than trusts; `tier_overrides` is writable only by `stratium_pap`, which
requires an operator's OIDC token; and the PDP holds `SELECT` alone (**T6**).
A pointer set covering fewer than all four is an overclaim.

`provenElsewhere` with machine-checked pointers is the likely honest
classification, since these live at layers `internal/authz` cannot reach. **Do
not force a pass** — C23 converted only when a real Envoy proved it, and five
others were left skipped with honest reasons.

Report the resulting tally. C17 and C25 remain, and both name real subsystems.

Confirm the conformance gate still bites: rename a pointed-to test, watch it
fail, restore.
