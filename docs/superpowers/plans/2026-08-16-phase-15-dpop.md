# Phase 15 — Sender-constrained tokens (DPoP)

Implements spec §4.7.2 **K5**–**K10**. Closes conformance property **C25**.
Seven tasks.

**Why this now.** §4.1.1 states that sender-constrained tokens are *"a
prerequisite for `proxy` and `extauthz`, not an independent later concern."*
Both surfaces shipped — Phases 10 and 11 — and the prerequisite was never met.
This is the debt those phases took on.

**State the gap accurately, because overstating it would misdirect the work.**
Tokens are already ECDSA-signed JWTs the PDP both issues and verifies (**K1**,
**K2**), and a token is an authenticated *reference* whose delegation the PDP
loads and evaluates in full (**K3**). An agent cannot mint a token naming a
delegation it was not granted — §4.1.1's worst fear, an agent choosing its own
authority, is already prevented by the signature. **What remains is replay after
theft**: a bearer token that leaks from a log, a proxy, or a compromised sidecar
is fully usable by whoever holds it, on exactly the two surfaces where the
request arrives from the party being policed.

**The shape of the work.** RFC 9449. A client generates a keypair and presents
the public JWK at `IssueToken`; the token carries `cnf.jkt`, the RFC 7638
thumbprint. On each request the client sends a proof JWT signed with the private
half, naming the method (`htm`), the URI (`htu`), a timestamp, and a unique
`jti`. The PDP verifies the proof, matches the thumbprint against the token, and
spends the `jti`.

## Global constraints

- Go 1.25, module path `stratium`, module root `services/`.
- **The PDP verifies; the PEP forwards** (**K7**, and **K2** before it). A PEP
  that decides a proof is valid is a PEP making an authorization decision —
  spec defect **D1**. The PEP extracts the proof and reports the method and URI
  it observed; it validates neither.
- **`internal/authz` stays pure**, and is not touched by this phase **except for
  `conformance_test.go`'s own outcome bookkeeping in Task 7** — that file lives
  in the package but records conformance state rather than participating in a
  decision. No production file in `internal/authz` changes. The proof package is
  likewise pure: no I/O, no ambient clock — the time is passed in, as
  `internal/authz` already does.
- **Fail closed.** A missing proof, a malformed proof, a thumbprint mismatch, a
  stale timestamp, a spent `jti`, or a failed `jti` write — every one denies. **A
  replay check that fails open is not a replay check.**
- **No `WHERE tenant_id` in any Go query.** RLS is the only tenant boundary.
- **A DPoP proof never reaches `raw_input` or the audit chain** (**K10**), the
  same rule `authorization` already has. Strip by omission, case-insensitively,
  and assert the absence structurally.
- **Never log a token, a proof, a private key, or a thumbprint.**
- **The PDP's grants on authorization configuration do not change** (**N3**,
  **E7**, **T1**, **T6**). The `jti` table is the one new write and §4.7.2
  **K8** states why it is not configuration.
- Strict root `.golangci.yml`. Clean before each commit, from the repo root:
  `make build`, `make vet`, `make test`, `make lint`, `make conformance`,
  `make integration`. Go targets route through `make` because the admin UI is
  embedded.
- **Commit before running any mutation.** Gate mutants on `go vet ./...`, which
  compiles test files, not `go build ./...`, which does not. If you change or
  delete a test, re-run every mutation it was credited with killing.
- Conventional commits, no attribution trailers.
- Scratch work goes in the session scratchpad, never the repository.

## Task 1 — The proof, verified: a pure package

**Files:** `services/internal/dpop/` (new), and tests. **No I/O.**

Parse an RFC 9449 proof JWT and answer one question: is this proof
well-formed, self-consistent, and fresh?

- The header must carry `typ: dpop+jwt`, an asymmetric `alg`, and the public
  `jwk`. **Reject `none` and any symmetric `alg` explicitly** — an `alg` the
  verifier accepts but the spec forbids is the classic JWT defeat.
- The signature must verify **against the `jwk` in the proof's own header**.
  That sounds circular and is not: it proves the sender holds the private half
  of *that* key. Binding it to the *right* key is `cnf.jkt`'s job, in Task 4.
- Compute the **RFC 7638 thumbprint** of the JWK — lexicographic member
  ordering, no whitespace, SHA-256, base64url. Get this exactly right; a
  thumbprint that disagrees with every other implementation's binds nothing.
- Claims: `htm`, `htu`, `iat`, `jti`. Check `iat` against a caller-supplied
  clock and a caller-supplied window. **The window is a parameter, not a
  constant** — Task 4 supplies it from configuration (**K9**).
- `htu` comparison follows RFC 9449: scheme and host case-insensitive, path
  exact, **query and fragment ignored**. State this in the doc comment; a
  reader will assume string equality.

**This package decides nothing about authorization.** It reports facts about a
proof. The compound decision stays in `internal/authz`.

**Tests:** a valid proof verifies; a wrong-key signature fails; `alg: none`
fails; a symmetric `alg` fails; a missing or wrong `typ` fails; each absent
claim fails; an `iat` outside the window fails in both directions; thumbprints
match RFC 7638's own worked example; `htu` matching ignores query and fragment
but not path.

**Mutation-test and report survivors:** accept `alg: none`; compare the
thumbprint with unordered JSON members; make the `iat` check one-sided; compare
`htu` with full string equality including query.

## Task 2 — Bind at issuance

**Files:** `proto/pdp/v1/pdp.proto`, `services/internal/pdpgrpc/token.go`,
`services/internal/token/`, and tests.

`IssueTokenRequest` gains an **optional** public JWK. When present, the issued
token carries `cnf: {jkt: "<thumbprint>"}`. When absent, the token is exactly
what it is today.

**The JWK is optional and the refusal lives at the surface** (**K6**).
`IssueToken` cannot know which surface will present the token it mints, so it
cannot decide whether binding is required. **K5** is what makes an unbound token
useless on the network surfaces, and that check belongs in Tasks 5 and 6. Do not
add a "surface" parameter to `IssueToken` to get around this — that would be a
client declaring how its credential should be treated.

**Reject a malformed JWK at issuance**, loudly. A token bound to a thumbprint
nobody can reproduce is a token that can never be used, and failing at
issuance is far cheaper to diagnose than failing on every later request.

**Existing bearer tokens keep working.** This is additive; every current caller
passes no JWK and sees no change. Prove that with a test rather than asserting
it.

**Tests:** a JWK yields a token carrying the right `cnf.jkt`; no JWK yields a
token with no `cnf` claim at all; a malformed JWK is refused at issuance; an
existing bearer flow is unchanged end to end.

**Mutation-test and report survivors:** emit `cnf` with an empty `jkt` when no
JWK is supplied; compute the thumbprint over the private key; accept a
malformed JWK and bind to a zero thumbprint.

## Task 3 — The `jti` store, and its reaper

**Files:** a migration, `services/internal/store/`, and integration tests.

A tenant-scoped table recording spent `jti` values with an expiry. Unique on
`(tenant_id, jti)` so a replay **collides at the database**, not in application
logic — the same argument this codebase makes everywhere else for a constraint
over a check.

**`GRANT INSERT, SELECT, DELETE` to `stratium_app` and nothing more.** §4.7.2
**K8** states why this does not contradict **E7**, **T1**, or **T6**: those
withhold writes on authorization *configuration*, because a PDP that could write
them would adjust its own authority. Replay state records that a proof was
spent, is written only by the component spending it, and no value in it can
widen a decision. **Put that reasoning in the migration**, where the next person
auditing the PDP's grants will look.

**RLS applies, as everywhere.** A `jti` spent in one tenant must not be visible
to another — and must not collide with the same `jti` in another tenant, which
is why the constraint is on the pair.

**Spending a `jti` is an insert that may collide.** Decide how a collision is
distinguished from any other write failure and say so — both deny, but an
operator debugging a replay storm needs to tell them apart. Do not use
`ON CONFLICT DO NOTHING` and then infer the outcome from a row count without
saying that is what you are doing.

**The reaper deletes expired rows on a schedule.** An unbounded table on the
decision path degrades every future request. **Its failure must be visible** —
a reaper that dies silently leaves a table that grows until something else
breaks, which is the failure mode nobody attributes correctly.

**Tests** (integration — a uniqueness constraint cannot be tested with sqlmock):
a first spend succeeds; the identical `jti` in the same tenant collides; the
same `jti` in a *different* tenant does not; expired rows are reaped; the reaper
leaves unexpired rows alone; `stratium_app` can insert, select, and delete, and
still cannot write `approvals`, `tool_catalog`, or `tier_overrides`.

**Mutation-test and report survivors:** drop the uniqueness constraint; make the
constraint `(jti)` alone and confirm a cross-tenant test notices; make a failed
insert allow; make the reaper delete unexpired rows.

## Task 4 — Verify in the PDP

**Files:** `proto/pdp/v1/pdp.proto`, `services/internal/pdpgrpc/`, config, and
tests.

`DecideRequest` gains the proof JWT and the **method and URI the PEP observed**.
The PDP verifies, in this order:

1. the proof is well-formed, correctly signed, and fresh (Task 1);
2. its thumbprint equals the token's `cnf.jkt`;
3. `htm`/`htu` equal what the PEP reported;
4. the `jti` has not been spent (Task 3), and is now spent.

**Order matters and is worth stating in code.** Spend the `jti` **last**, after
every cheaper check passes — spending it first means a malformed proof burns a
`jti` an honest client might legitimately retry with, and turns a garbage
request into a denial of service against that client.

**A token with no `cnf.jkt` is not an error here.** It is a bearer token, still
valid on the local surfaces. The PDP reports what it saw; Tasks 5 and 6 refuse
it where **K5** requires. Getting this wrong in either direction breaks
something: refusing here breaks `hook` and `mcp`, allowing it in Tasks 5 and 6
leaves the gap this phase exists to close.

**The freshness window is required configuration with no default** (**K9**), and
a missing value fails at startup naming every missing key at once, as every
other component does.

**Where this sits in `Decide`.** It is a credential check, like the token
signature check — it belongs with that, not among the three legs. **Do not
touch `authz.FoldVerdicts` or add a fourth leg**: the compound decision is
`principal ∧ agent ∧ delegation` and a credential that fails verification never
reaches it. Say in the code which of those two things you did.

**Tests:** a valid bound token plus a valid proof allows; a bound token with no
proof denies; a proof whose thumbprint does not match the token denies; a proof
naming a different method or URI denies; a replayed `jti` denies; an unbound
token still allows here; the `jti` is not spent when an earlier check fails; a
missing window config fails startup.

**Mutation-test and report survivors:** skip the thumbprint comparison; skip the
`htm`/`htu` comparison; spend the `jti` before the other checks; treat a
verification error as an allow.

## Task 5 — Wire `extauthz`

**Files:** `services/cmd/stratium-pep/extauthz.go`, and tests.

Extract the proof from the `DPoP` header. Forward it, plus the method and the
reconstructed URI, in the `DecideRequest`.

**Refuse a token with no `cnf.jkt`** (**K5**). This is the converse half of C25
and the one a test suite will miss: C25's own wording covers *"a bound token
presented without a proof"*, and the migration hole is the opposite case — an
unbound token, on a surface where binding is required. **Both need a test.**

**Reconstruct `htu` from what Envoy reports** — scheme, authority, path — and
be explicit about which header supplies each. Phase 10 found that real Envoy
passes `:method` and `:path` as literal header entries and injects
`x-forwarded-proto`; that is the material to build `htu` from, and a
hand-constructed `CheckRequest` will not tell you whether you got it right.

**The proof never reaches `raw_input`** (**K10**). `raw_input` is hashed into
the append-only audit chain. Strip `DPoP` by omission and case-insensitively,
exactly as `authorization` already is, and **assert the absence structurally
across several casings**.

**Tests:** a bound token with a valid proof reaches the upstream; the same token
with no proof denies; an unbound token denies with a distinguishable reason; the
`DPoP` header never appears in `raw_input` in any casing; `htu` matches what the
PDP validates against.

**Mutation-test and report survivors:** allow an unbound token; leave `DPoP` in
`raw_input`; build `htu` from the wrong header; strip case-sensitively.

## Task 6 — Wire `proxy`

**Files:** `services/cmd/stratium-pep/proxy.go`, and tests.

The same, over gRPC metadata rather than HTTP headers.

**`htu` is the proxy's own address plus the full method path**,
`/package.Service/Method`, with `htm` as `POST` — gRPC is HTTP/2 POST (§4.7.2
**K7**). **Binding to the target's address instead would let a proof for one
target be replayed at another behind the same proxy**, which is the whole point
of binding. Test that specifically.

**A stream is authorized once, at open** (**P4**), so the proof is checked once,
at open. One decision, one `jti`. State plainly that a long-lived stream rides
one proof, because an operator will assume per-message binding and there is no
way to provide it without target schemas.

**Tests:** a bound token with a valid proof forwards; no proof denies and does
not forward; an unbound token denies; a proof built for a different target is
refused; `htu` uses the proxy's address, not the target's; a stream is
authorized once at open; metadata never leaks the proof into `raw_input`.

**Mutation-test and report survivors:** use the target's address in `htu`;
re-check the proof per message on a stream and confirm what breaks; allow an
unbound token.

## Task 7 — Prove it, and close C25

**Files:** `deploy/docker/`, the integration suite,
`services/internal/authz/conformance_test.go`.

**Against a live stack**, with a real client holding a real keypair:

1. A bound token with a valid proof is allowed through **both** network
   surfaces.
2. The same token with **no** proof is denied — C25 as written.
3. An **unbound** token is denied on both surfaces — **K5**, the converse half.
4. A **replayed** proof is denied, proven by sending the identical proof twice
   and confirming the second is refused for replay rather than for anything
   else.
5. A proof **stolen and presented from elsewhere** — same token, same proof,
   different method or URI — is denied. This is the property the whole phase
   exists for; make it the one that most obviously bites.
6. `hook` and `mcp` still work with **unbound** tokens, unchanged. A phase that
   silently breaks the local surfaces has failed regardless of what it proved
   about the network ones.
7. The `DPoP` header does not appear in the audit row's input digest source,
   proven against a real request rather than a constructed one.

**Then close C25.** Read what it asserts: *"a delegation token without a valid
DPoP proof is denied when the token is sender-constrained."* Proof 2 establishes
exactly that. Decide honestly whether it converts to `pass` or to
`provenElsewhere` with a machine-checked pointer — the property is exercised at
a layer `internal/authz` cannot reach, which has meant `provenElsewhere` for
every comparable property in this suite. **Do not force a pass.**

Report the resulting tally. **C17 remains** and names a real subsystem
(crypto-shredding and per-tenant key management); confirm its reason is still
accurate rather than assuming.

Confirm the conformance gate still bites: rename a pointed-to test, watch it
fail, restore. Note that `make conformance` only became a real gate in Phase 14
Task 8 — before that it exited 0 on a failing property — so this check is worth
running rather than trusting.

Tear everything down; verify no stray containers.
